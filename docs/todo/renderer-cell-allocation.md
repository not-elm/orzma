# レンダラーのセル変換における確保コスト

記録日: 2026-09-13 / 対象リビジョン: `b395a185`

`TerminalGrid` を `TerminalView` / `TerminalCells` へ分割した PR のコードレビューで
挙がった指摘の調査記録。**この PR では修正しない。** 修正は別 PR で対応する。

指摘の元の文言は「`runs_to_cells` が dirty 行ごとに固定幅の `Vec<GridSlot>` を
毎フレーム確保し、`apply` が置き換え対象の行バッファを捨てている。50 行 60Hz で
約 3000 回/秒のアロケータ往復」だった。**この数字は件数を約 `cols` 倍、
秒間往復を 280〜560 倍過小評価している。**

## 1. 測定結果

カウンティンググローバルアロケータを仕込んだ release ビルドで、実際の
`OrzmaVt` にバイト列を流して測定した（計測コードは調査後に削除済み）。

200 列 × 50 行:

| シナリオ | `TerminalCells::apply` | VT 側 `FrameTracker::emit` |
|---|---|---|
| 全再描画・プレーンテキスト | **10,050 alloc / 10,050 free / 730,000 B** | 401 alloc / 46,050 B |
| dirty 1 行 | **201 alloc / 201 free / 14,600 B** | 9 alloc / 1,017 B |
| 全再描画・セルごとに SGR run（重い TUI） | 10,050 / 10,050 / 730,000 B | **10,301 alloc / 1,221,200 B** |

### 件数とバイト数は別の軸で分かれる

| 内訳 | 件数 | バイト数 |
|---|---|---|
| 行 `Vec<GridSlot>` × 50 | 0.5% | **98.6%**（720,000 B） |
| グラフェム `String` × 10,000 | **99.5%** | 1.4%（10,000 B） |

行 `Vec` は 14,400 B の大きなブロックが 50 個、グラフェム文字列は約 1 バイトが
10,000 個。**レビューの指摘はバイト数について正しく、件数については誤っている。**
行 `Vec` だけ直すと件数は 0.5% しか減らない。

### 10,000 という数の根拠

`Row::to_runs` は**空白の末尾も含めて行全体**を run 化する
（`crates/orzma_vt/src/screen/grid/row.rs:217` のテストが固定している）。
そのため空白だけの行でも `runs_to_cells` は全 200 列に `String` を持つ
`GridCell` を作る。10,000 / 50 = 200 = `cols`。

### 秒間コスト

フレーム発行はコアレサに律速される（`crates/orzma_tty/src/coalescer.rs:38-40`、
3ms アイドルのデバウンス / 12ms のハードキャップ）。連続出力で約 83 フレーム/秒、
バースト時で最大約 333 フレーム/秒。全再描画フレームなら
10,050 × 83 ≈ **834,000 alloc/秒/ペーン**、free を含めて約 167 万往復/秒。
malloc/free 対あたり約 25ns として**全再描画フレームあたり 0.4〜0.6ms**。

## 2. 全再描画の頻度

満杯の画面で最終行にプロンプトがある通常のシェル状態に対し、実際のバイト列を
流して測定した結果:

| 入力 | フレームに含まれる行数 |
|---|---|
| 1 文字打鍵 | **1** |
| Enter（CR+LF） | **50** |
| `ESC[2J`（消去） | 50 |
| 代替画面の出入り | 50 / 50 |
| `ESC[S`（SU）/ `ESC[L`（IL） | 50 / 50 |
| `ESC c`（RIS） | 50 |
| ビルド出力 3 行を 1 コアレス窓に | **50** |

機構: 下マージンでの `line_feed` が `scroll_region_up` → `shift_rows_up` に委譲し、
これが無条件に `DamageSpan::Full` を返す
（`crates/orzma_vt/src/screen.rs:408-411, 606`）。

**画面をスクロールさせる出力はすべて全再描画になる。** `cargo build` や `cat` は
10,050 確保フレームの連続。1 行で済むのは改行と改行の間の打鍵だけ。
`TerminalCells::differs_from` はこれを抑制しない
（`rows.iter().any(|row| row.line.0 < size.rows)`、`schema/grid.rs:281`）。

## 3. 構造体サイズ

実測で `size_of::<GridCell>() == size_of::<GridSlot>() == 72`、align 8。
enum のタグは `Color` のニッチが吸収するので `GridSlot` は無料。
`String` が 24 B、`Option<Hyperlink>` が **32 B**（セルの 44%、しかも現状は常に `None`）。

| 形 | スロットサイズ | 200×50 の保持グリッド |
|---|---|---|
| 現状（`String` + `Option<Hyperlink>`） | **72 B** | 703 KiB |
| `Option<HyperlinkId>` に変更 | **48 B** | 468 KiB |
| `char` + 稀な尾部を箱詰め（Alacritty 形） | **40 B** | 390 KiB |
| `char` のみ、マークビットを `style` に畳む | **24 B** | 234 KiB |

`SmolStr` / `CompactString` はどちらも 24 B で `String` と同じなので、ここは変わらない。

**GPU 側は既に妥当**: orzma の `GpuCell` は 20 B（`material.rs:1220` で assert）で、
kitty の `GPUCell` も 20 B。過大なのは CPU 側ミラーだけ（72 B 対 kitty の 12 B）。

## 4. 保持が必要な最小情報

`GridCell.text` の本番読み手は 3 箇所だけ。

| 箇所 | 読む範囲 |
|---|---|
| `resolve_glyph_index`（`material.rs:1038`） | `cell.text.chars().next()` — **先頭 char のみ** |
| `style_from_combining_marks`（`material.rs:1010-1026`） | クラスタ全体。ただし U+0331/0332/0333 → `UNDERLINE`、U+0336 → `STRIKE` の 4 つだけ |
| `GridCell::is_blank`（`schema/grid.rs:36`） | `text.trim().is_empty()` |

つまり最小限は**先頭 `char` + 2 ビット**。

副次的な改善余地: マーク → スタイルの畳み込みは現在 `rebuild_cells` にあり、
GPU 再構築ごとに全 10,000 セルに対して走る。`runs_to_cells`（dirty 行のみ）へ
移せる。

## 5. クラスタ長は 0〜800 バイトの範囲で無制限

コードベース内にクラスタ長を縛るものは無い。`orzma_vt::Cell` は単一 `char`
（`crates/orzma_vt/src/screen/cell.rs`、クラスタ保持の TODO 付き）、
`print` は幅も結合文字も濾さない（`interpreter.rs:105`）、`graphemes(true)` に上限は無い。

測定値:

- `a` + U+0301 × 199 → `text.len() == 399` の `GridCell` 1 個が列 0 を占め、残り 199 列は `Empty`
- ZWJ 家族絵文字 `👨‍👩‍👧‍👦` → 1 クラスタで **25 バイト / 7 char**

上限は `cols × 4` バイト。**25 バイトは `SmolStr` の 23 バイトも `CompactString` の
24 バイトもインライン上限を超える**ので、どちらのクレートでもヒープに落ちる。
固定長インライン配列は panic か切り捨てになる。

### Alacritty の DoS には晒されていない

`echo -en a; (while true; do echo -en '\xcc\x81'; done)` は、`orzma_vt::Cell` が
セルあたり 1 `char` で `print` がカーソルを無条件に進めるため、1 セルに積み上がらず
列方向に広がって折り返す。各行は列 0 に約 399 バイトのクラスタ 1 個、残りは `Empty`。
総量は `rows × cols × 4` ≈ 40 KB で有界。VT のスクロールバックは固定 16 バイトの
`Copy` セルを持つ。**メモリ枯渇ベクタではない。**

## 6. ハイパーリンク経路は死んでいるが、将来の確保を予約している

`Run::hyperlink_id` は「常に `None`」と文書化されて TODO 付き
（`crates/orzma_vt/src/screen/grid/run.rs:39-42`）、`Frame::hyperlinks` は
「常に空」（`crates/orzma_vt/src/frame.rs:56-63`）、`Row::to_runs` は
`hyperlink_id: None` をハードコード（`row.rs:53`）。よって
`schema/grid.rs:393` の `hyperlink.clone()` は現在ゼロ確保。

**ただし** `schema/grid.rs:377` の `uri: uri.clone()` は**セルごとの `String` クローン**。
OSC 8 が実装されると、全リンクの行で行あたり `cols` 回の確保が増える。

消費者は 2 つだけで、どちらも id しか要らないか、テーブルを既に持っている。

- `TerminalCells::hyperlink_at`（`schema/grid.rs:254`）— URI が必要だが `lookup_hyperlink` とテーブルを既に持っている
- `rebuild_cells`（`material.rs:972`）— `h.id.0` **のみ**

`Option<HyperlinkId>` に変えれば挙動は同一。

### 1+3 融合の唯一の実コスト

セルの `String` を再利用すると容量が残る。399 バイトのクラスタを一度持った
セルは 399 バイトの容量を保持し続ける。200×50 の敵対的最悪ケースで約 8 MB。

緩和策は、**入ってくるグラフェムが既存容量に収まり、かつ小さい閾値
（8 バイト程度）以下のときだけ再利用し、それ以外はセルを置き換える**こと。
ホットパスの分岐予測も効きやすくなる。クラスタ長に上限を設ける（第 9 節）なら
最悪ケースは `cap × 4` バイト/セルに落ちる（200×50 で約 100 KB）。

### Ghostty の quadratic 警告は orzma には当てはまらない

Ghostty の `appendGrapheme` は上限を設ける理由をこう書いている。

> Terminal input is untrusted. In addition to bounding memory, this prevents
> repeated chunk growth and copying from becoming quadratic.

これはコードポイントを 1 つずつ**逐次追加**する設計に固有の危険。
`runs_to_cells` は既に完成した行文字列からセグメントし、クラスタごとに
`to_string()` を 1 回だけ行う（`schema/grid.rs:380-389`）。推奨する
`clear()` + `push_str()` も完成したクラスタの 1 回コピー。**二次関数化の危険は無く、
むしろ推奨案が正しい形であることの裏付けになる。**

### 規約適合

`refill_row(out: &mut Vec<GridSlot>, …)` は `()` を返すので
「ローカル型を構築する関数は associated function」の規約は不適用。
mutable-first も満たす。private helper は `pub` 項目の下に置く。
doc コメントには観測可能な契約（「`out` を正確に `cols` スロットで埋め、
元の内容を置き換える」）だけを書き、理由（「再確保を避けるため」）は書かない。

## 8. 先行事例

各リポジトリのソースを SHA 固定で検証した。

| | セルあたり | 主文字 | クラスタ尾部 | 上限と超過時の挙動 |
|---|---|---|---|---|
| **Ghostty** | **8 B**（`packed struct(u64)`） | u21 インライン | ページごとのアリーナ側テーブル、**セルオフセットがキー** | **64 コードポイント**、超過は黙って無視。テスト 2 本で固定 |
| **Kitty** | **12 B** CPU + 20 B GPU | `ch_or_idx:31` + `ch_is_idx:1` | コードポイント**列**を `TextCache` で intern | **24 コードポイント**、超過は追加を拒否 |
| **Alacritty** | **≤ 24 B** | `char` | `Option<Arc<CellExtra>>` 内の `ArrayVec<char, 9>` | **9 個**、黙って切り捨て |
| **WezTerm** | **24 B** | `TeenyString(u64)`、7 B インライン UTF-8 かつ幅 < 3 | ヒープ `Box<TeenyStringHeap>` | 上限は見つからず |
| **orzma 現状** | **72 B** | `String`（常にヒープ） | 同じ `String` | 上限なし、実測 399 B |

**4 実装すべてが単一コードポイントのケースでヒープ確保をしない。**
セルあたり `String` を持つ実装は 1 つも無い。

### 教訓 4 つ

1. **コードポイントを保持せよ、テキストではなく。** 4 つのうち 3 つがコードポイントか
   インデックス。WezTerm だけがテキストを持つが `u64` に詰めている。
2. **Alacritty はハイパーリンクを稀なサイドボックスに置いている。** `CellExtra` の
   doc コメントが逐語でこう述べる: 「稀に設定されるセル属性のための領域。
   全セルで事前に確保する量を削減できる」。その構造体は
   `{ zerowidth, underline_color, hyperlink }`。インライン `[char; 5]` から
   `Option<Box<CellExtra>>` へ移した際、常駐メモリが **1.06G → 733M（−30%）**。
   これは第 7 節の 7a / 4′ に測定済みの前例が付いたことを意味する。
3. **intern するなら回収を最初から設計せよ。** kitty の `text-cache.h` が
   「一意なセルテキストを永久に intern するので、多コードポイントセルの流入で
   無制限に増える」と自ら文書化している。`tc_should_gc` は intern 設計の出荷から
   約 19 か月後の v0.48.0 で初めて現れた。
4. **Alacritty は orzma のモデルにならない。** グラフェム分割を一切せず、
   コードポイント単位の `unicode-width` だけで分岐する（`term/mod.rs:1062-1085`）。
   幅 2 の絵文字ベースごとに新セルが始まるので、ZWJ 家族絵文字は**4 つの wide セル /
   8 列**になり、9 上限は ZWJ には効かない。orzma は `graphemes(true)` で分割する
   ので WezTerm / Ghostty 側。

### 4 実装すべてが CPU 側消費者に「借用」を渡している

セルのテキストを必要とする CPU 側の読み手に対し、4 実装は所有文字列を作らない。

| | CPU 消費者への受け渡し |
|---|---|
| Kitty | `text_in_cell_without_alloc` — **確保が必要なら false を返す**。4 コードポイントのスタックバッファ（`RAII_ListOfChars`）と、`Screen.lc` という長命の再利用バッファを併用 |
| Ghostty | ページメモリへ借用した `[]u21` |
| Alacritty | `Option<&[char]>` |
| WezTerm | 行の `String` から借用した `&str`。シェーピングは内容ハッシュをキーにする |

**この一致こそが発見である。セルあたり所有 `String` という変換は、4 実装のどこにも存在しない。**

Kitty はレンダラー側の問いにも構造で答えている。`GPUCell`（20 B、`static_assert` 付き）は
`sprite_index` を持ちテキストを**一切持たない**。`ch_or_idx` を持つ 12 B の `CPUCell` は
CPU から出ない。orzma も `GpuCell` は 20 B で同じ形だが、CPU 側ミラーだけが 72 B。

### テキストを保持する唯一の文書化された論拠は、描画のためではない

WezTerm のコミット `d5d161b51093` はクラスタ化保持を「テキスト内容の照合・抽出」と
検索の安さで正当化している。**そして利得はテキストを*行*へ引き上げたことから来ており、
セルに保持することからではない。** セルあたりのテキストは、そのコミットが回避した対象。

どのプロジェクトも「テキストではなくコードポイントを選んだ理由」を文書化していない。
文書化されていたのはセルあたりバイト数の測定と、信頼できない入力への上限だった。
つまりセルに所有テキストを置く設計には、先行事例からの擁護が存在しない。

### Ghostty 形は構造的に採用できない

Ghostty の側テーブルは**セルオフセットがキー**なので、消去・スクロール・リフローで
マップを補修する必要がある。orzma は dirty 行のスロットを毎フレーム丸ごと置き換える
ため、セルキーの側テーブルは再充填ごとに無効化が必要になる。

### `runs_to_cells` は存在意義がある

WezTerm の `ClusteredLine`（行ごとに 1 本の UTF-8 `String` + ランレングスの属性
クラスタ + wide 列の箱詰めビットセット）は、**orzma が VT から `Row<Run>` として
既に受け取っている形とほぼ同じ**。WezTerm はスクロールバック圧縮のために行を
その形へ**変換している**（2.1G → 620M）。つまり `runs_to_cells` は解凍ステップで、
GPU 再構築が列単位のランダムアクセスを要するため必要。これは 7b（ワイヤ形式の変更）
を強めるのではなく**弱める**。

## 9. 隣接する発見（行 `Vec` よりバイト数が大きい）

`material.rs:928` の `buf.set_data(std::mem::take(&mut state.cpu_cells))` は
再利用バッファを**手放している**。そのため `material.rs:914` の
`cpu_cells.resize(cell_count, …)` が毎アップロードで 200,000 B の Vec を新規確保する。
さらに Bevy の `ShaderBuffer::set_data`
（`bevy_render-0.19.0/src/storage.rs:81-89`）が encase で**もう 1 本**
`Vec::with_capacity(size)` に再エンコードする。

**1 アップロードあたり約 400 KB** で、50 行分の行 `Vec` 合計 720 KB に匹敵する。
参照を渡す形にすれば 1 行で半分回収できる。

## 10. 推奨順序

1. **選択肢 1+3 の融合** — `runs_to_cells` が `&mut Vec<GridSlot>` を再充填し、
   生き残るセルの `String` を `clear()` + `push_str()` で上書きする。実測ゼロ確保。
   依存追加なし、公開 API 変更なし、サイズ変更なし、切り捨てリスクなし。
   容量保持の緩和策を同時に入れる。
2. **`Option<Hyperlink>` → `Option<HyperlinkId>`** — 独立・機械的、72 → 48 B
   （200×50 で −235 KiB）。OSC 8 が持ち込む予定のセルごと `String` クローンを
   先に潰す。Alacritty の設計と −30% の実測が後ろ盾。
3. **クラスタ長の上限（分離可能）** — 堅牢性の問題。DoS ではない（第 5 節）。
   #1 の容量保持の最悪ケースを約 8 MB → 約 100 KB に落とす副効果がある。
4. **それ以上はプロファイルが要求するまで不要。** 24 B / 40 B の形はいつでも取れ、
   #1 と両立する。#1 が既にゼロ確保に到達するので、それらが買うのはメモリであって
   アロケータ負荷ではない。

やらないこと: 小文字列クレートの追加（0 に届かず、インライン上限も家族絵文字に負ける）、

## 12. やる価値はあるか

正直な枠組みで言えば、ある。

全再描画フレームあたり 0.4〜0.6ms のアロケータ作業は、83〜333 フレーム/秒でも
今日ユーザに見える停止ではない。ボトルネックであるというプロファイルも無い。
しかし #1 は 1 ファイル約 45 行で、依存ゼロ・公開 API 変更ゼロ・サイズ変更ゼロ・
切り捨てリスクゼロ、**実測でちょうどゼロ確保**。この比率はレビュワーが
受け入れるべき水準。

PR に書くべき留保: 重くスタイル付けされた TUI では VT 側の `Row::to_runs` が
同じフレームで独立に 10,301 回確保するため、この修正は全体を半減させるだけ。
そこに手を付けるには `orzmux` チャネルを流れるものを変える必要があり、別個かつ
遥かに大きな判断になる（7b、ただし第 8 節の WezTerm の事例はこれを弱める）。

## 13. 訂正の記録

調査中に覆った枠組みを残す。同じ誤りを繰り返さないため。

- **レビューの「行あたり alloc 1 回」は誤り。** `Row::to_runs` が空白の末尾も
  run 化するため、通常の行では painted grapheme 数 = 列数になる。
- **「行 `Vec` の修正が問題の本体」も誤り。** 件数では 0.5%。ただしバイト数では
  98.6% なので、どちらの見方も半分正しい。
- **「Ghostty の untrusted input 論により上限は前提条件」も誤り。** Ghostty の
  警告は逐次追加設計に固有で、orzma の 1 回コピー設計には当てはまらない。
  上限は堅牢性の改善であって前提条件ではない。
- **「orzma は Alacritty の DoS に晒されている」も誤り。** セルあたり 1 `char` と
  無条件のカーソル前進により、攻撃は列方向に広がって有界になる。
- **Alacritty の zerowidth ベクタは無制限ではない。** 2026-08-26 のコミット
  `ede2ac144da4` で 9 個に上限が設けられた（DoS 修正）。6 年間無制限で出荷され、
  後から修正された経緯そのものが教訓。
